# Custom Validation Rules

Custom rules are Fleet's **extension mechanism for CORE** — start with
[Validation with CORE](validation-core.md) for the base engine setup and the
official rule sets. When the standard CDISC CORE conformance rules do not
cover a study-specific requirement — a sponsor SOP constraint, an FDA
Technical Conformance Guide (TCG) gap, a protocol-specific range check, or
ADaM checks while the official ADaMIG rule set remains unpublished — you
author **custom rules** and run them alongside (and in the same engine as)
the official rules.

---

## When to write custom rules

- **Sponsor SOPs** require checks not covered by CDISC CORE (e.g. mandatory SUPPQUAL variables).
- **FDA TCG requirements** that have not yet been formalised as CORE rules.
- **Protocol-specific constraints** such as custom reference ranges, visit windows, or dose limits.
- **Interim quality gates** during study setup before official validation.

---

## Quick start

### 1. Configure the custom rules directory

In your `study_config.yaml`, set the `custom_rules` path:

```yaml
validation:
  custom_rules: metadata/custom_rules  # directory for your .yaml rule files
```

`fleet init cfg` sets this up by default. The engine loads **all `.yaml` files** in this directory.

### 2. Scaffold a new rule

```bash
# Auto-increments ID: FLEET-AE-001, FLEET-AE-002, …
uv run fleet add-rule --domain AE --description "AESEV must be populated when AESER = Y"

# Custom prefix
uv run fleet add-rule --domain AE --prefix ROCHE --description "Severity required for serious AEs"

# Explicit ID (skips auto-increment)
uv run fleet add-rule --domain VS --id ROCHE-VS-010 --description "VSORRES range check"

# Output to a specific directory (overrides study_config)
uv run fleet add-rule --domain AE --description "Custom check" --output ./my_rules/
```

### 3. Edit the Check block

Open the generated YAML and fill in your validation logic in the `Check:` section:

```yaml
Check:
  all:
    - name: AESER
      operator: equal_to
      value: "Y"
      value_is_literal: true
    - name: AESEV
      operator: empty
```

### 4. Run validation

```python
# Inline in a pipeline
ae = (
    raw_df.sdtm.assign("DOMAIN", value="AE")
    .validate("AE", custom_rules="metadata/custom_rules")
    .to_frame()
)

# Or via the ValidationService
from fleet.validation.service import ValidationService

svc = ValidationService()
result = svc.validate_sdtm(ae, domain="AE", custom_rules="metadata/custom_rules")
result.print_report()
```

## Rule anatomy

A custom rule follows the same YAML schema as CDISC CORE rules. Here is an annotated example:

```yaml
Core:
  Id: FLEET-AE-001          # Unique ID (auto-generated by fleet add-rule)
  Status: Draft
  Version: "1"

Rule Type: Record Data       # Record-level check

Scope:
  Classes:
    Include: [EVENTS]
  Domains:
    Include: [AE]            # Restrict to the AE domain

Check:                       # The validation logic (what you write)
  all:
    - name: AESER
      operator: equal_to
      value: "Y"
      value_is_literal: true
    - name: AESEV
      operator: empty

Outcome:
  Message: >-
    AESEV is empty for a record where AESER = 'Y'. Serious adverse events
    must have severity documented.
  Output Variables: [USUBJID, AETERM, AESER, AESEV]

Description: >-
  AESEV must be populated when AESER = 'Y'.

Authorities:
  - Organization: Fleet
    Standards:
      - Name: SDTMIG
        Version: "3.4"
        References:
          - Origin: Sponsor SOP
            Rule Identifier:
              Id: FLEET-AE-001
              Version: "1"

Sensitivity: Record
Executability: Fully Executable
```

## The check DSL

CDISC CORE rules use a JSON/YAML check DSL built from composable operators:

| Combinator | Meaning                             |
| ---------- | ----------------------------------- |
| `all`      | All conditions must be true (AND)   |
| `any`      | At least one condition is true (OR) |
| `not`      | Negates the enclosed condition      |

Each leaf condition specifies a **variable name**, an **operator**, and optionally a **value**:

```yaml
Check:
  all:
    - name: AESEV
      operator: is_contained_by
      value: ["MILD", "MODERATE", "SEVERE"]
    - name: AESER
      operator: equal_to
      value: "Y"
      value_is_literal: true
```

### Available operators

| Operator | Description |
|----------|-------------|
| `equal_to` | Exact match |
| `not_equal_to` | Not equal |
| `empty` | Variable is null/blank |
| `non_empty` | Variable has a value |
| `less_than` / `greater_than` | Numeric/date comparison |
| `less_than_or_equal_to` / `greater_than_or_equal_to` | Inclusive comparison |
| `contains` / `does_not_contain` | Substring check |
| `is_contained_by` | Value is in a list |
| `starts_with` / `ends_with` | Prefix/suffix check |
| `matches_regex` | Regex pattern match |
| `date_less_than` / `date_greater_than` | Date comparison |

For the full operator reference, see the [CDISC CORE Rule Editor](https://rule-editor.cdisc.org/).

## Configuration and resolution order

Fleet resolves custom rules from multiple sources. The first match wins:

1. **Explicit `custom_rules=` parameter** on `.validate()` or `ValidationService` methods.
2. **`validation.custom_rules`** in `study_config.yaml` (team-wide default).
3. **None** — no custom rules are loaded.

## Storing custom rules

Place custom rule files in the configured directory (default: `metadata/custom_rules/`):

```
my_study/
  study_config.yaml
  metadata/
    custom_rules/          ← Your sponsor-specific rules (all .yaml files loaded)
      FLEET-AE-001.yaml
      FLEET-AE-002.yaml
      ROCHE-VS-001.yaml
    sdtm/
      rules/               ← CDISC CORE rules (from fleet init rules)
    adam/
      rules/
```

Commit the directory to VCS so the complete rule inventory is versioned alongside the study.

## ID naming convention

| Pattern | Example | Owner |
|---------|---------|-------|
| `CORE-XXXXXX` | `CORE-000001` | CDISC (official — never reuse) |
| `<COMPANY>-<DOMAIN>-<NNN>` | `ROCHE-AE-001` | Your organisation |
| `FLEET-<DOMAIN>-<NNN>` | `FLEET-DM-003` | Default prefix |

The `--prefix` flag on `fleet add-rule` controls the prefix. Auto-increment scans existing
rules in the target directory to determine the next available sequence number.

### Uniqueness guarantee

`fleet add-rule` checks all existing `.yaml` files in the target directory and refuses to
create a rule if the `Core.Id` already exists. This prevents accidental overwrites.

## Validating rule schema locally

Before running rules through the engine, you can validate them against the vendored CDISC
JSON Schema:

```python
import json
import yaml
from jsonschema import Draft202012Validator
from pathlib import Path

schema_path = Path("src/fleet/validation/schemas/cdisc_rule_schema.json")
schema = json.loads(schema_path.read_text())

with open("metadata/custom_rules/FLEET-AE-001.yaml") as f:
    rule = yaml.safe_load(f)

validator = Draft202012Validator(schema)
errors = list(validator.iter_errors(rule))
# errors == [] means the rule is schema-valid
```
